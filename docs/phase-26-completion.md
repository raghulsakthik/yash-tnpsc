# Phase 26 Completion Report — TNPSC PYQ Intelligence & Question Content Engine

## Scoping this honestly, first

This phase's brief (26.1-26.7) assumes real TNPSC PDF source documents, an OCR/NLP toolchain, and a reachable generative AI provider. None of those exist in this repository or sandbox: no PDFs are checked in, no OCR library is installed, and (confirmed directly) `ANTHROPIC_API_KEY` is unset in this environment. Building a full PDF→OCR→classification pipeline or a working MCQ generator without any of that would mean fabricating either tooling that doesn't function or question content not grounded in a real source — both direct violations of this project's standing rule, reinforced since Phase 20's comment in `content/syllabus/prelims-495.yaml`: "never invent a weight."

What the repository *does* already have, real and substantial: **137 real, hand-transcribed TNPSC Group 2 past-paper questions**, tagged `source: tnpsc-YYYY` with a real per-question `year`, spanning seven real years (2013, 2015, 2016, 2017, 2018, 2022, 2024) across Aptitude and Reasoning — seeded since Phases 20/21, validated by the existing `validate-content.mjs`. This phase builds the genuinely new intelligence and tooling layers on top of that real data, and is explicit everywhere else about what would need real source material or a configured AI provider to go further.

**A mid-build correction worth recording**: partway through, a real (if currently unconfigured) generative AI provider wrapper was discovered already in the codebase from an earlier phase — `src/lib/ai/provider.mjs` (plain `fetch` to Anthropic's Messages API, gated on `ANTHROPIC_API_KEY`), `src/domain/ai/context.mjs`, an `ai_interaction` cache table (`V4__ai_interaction.sql`), and `POST /api/ai/hint` (a single mistake-triggered explanation, cached per question). This phase's own 26.4 module had been drafted with a comment implying no AI infrastructure existed at all in this project — inaccurate, caught before shipping, and corrected: the accurate statement is that a real provider *path* exists, it degrades to `null`/unavailable exactly the way this phase's own deterministic fallback does, and it simply isn't reachable in this sandbox (no key). `/api/ai/hint`'s own cache (HINT/EXPLANATION types, one per question) is narrower in shape than what 26.4 asks for (per-question-and-stage progressive assistance, strategy, solve, similar-question) and was left untouched — this phase's new `/api/v1/ai/*` routes are additive, not a replacement.

## What was implemented

**26.1 — Ingestion.** `question` already stores Exam (`source`), Year (`source_year`), Subject/Chapter/Topic (via the existing `topic_id` FK chain), Difficulty, and Validation status (`status`) — all real, unchanged since Phase 1. `validate-content.mjs` already is the brief's "Question Detection/Option Detection/Subject Classification/Topic Classification/Difficulty Classification/Validation" pipeline, just driven by hand transcription instead of OCR — the honest, real approach for a small, legally-sensitive exam bank with no source PDFs on disk. New, additive, nullable columns (`db/migrations/V13__pyq_intelligence.sql`): `paper`, `question_number`, `source_page`, `content_version` — ready to receive real values the day actual paper scans are transcribed, left `NULL` on all 137 existing real rows rather than fabricated.

**26.2 — Knowledge Mapping.** `src/domain/pyqIntelligence.mjs` (pure reporting shapes) + `src/repository/pyqIntelligenceRepository.mjs` (real aggregate reads over `source LIKE 'tnpsc-%'`) + `src/services/pyqIntelligenceService.mjs`: real topic frequency, subject frequency, year-wise trends, difficulty distribution, and concept frequency — every frequency response carries the brief's own required disclaimer ("does not predict or guarantee future appearance"), and the yearly-trends response is explicit that gap years mean untranscribed, not a real zero.

**26.3 — Practice modes.** `src/repository/pyqCatalogRepository.mjs` + `src/services/pyqCatalogService.mjs`: year-wise/subject-wise/topic-wise/mixed/timed as one filtered list over the real catalogue; weak-area reuses Phase 4/6's own live classification (`getLearnerSummary()`, unchanged) rather than recomputing weakness; incorrect reuses real `question_attempt.correct = false` history. Answering a PYQ question is not a new flow — `POST /api/v1/pyq/:id/attempt` delegates entirely to the exact same `recordAttempt()` pipeline every other question uses (verified: a wrong real attempt updated real `learner_topic_state`/mastery/mistake-classification identically to any other practice attempt).

**26.4 — AI PYQ Solving Assistant.** `src/domain/pyqAssistant.mjs` + `src/services/pyqAssistantService.mjs`: deterministic progressive assistance (hint → strategy → guided solution → full explanation), why-right/why-wrong explanations (using the real authored `trap` when it's the option actually picked), and a real similar question (found via `findSimilarQuestion()` — an actual other question on the same topic in a comparable difficulty band, never generated text). Strictly read-only — verified directly that `learner_topic_state` is byte-identical before and after every assistant call.

**26.5 — TNPSC-Inspired MCQ Engine.** The storage/provenance/review framework is built (`generated_question` table — `source_pyq_ids`, `source_pattern`, `concept`, `generation_model`, `generation_version`, `validation_status`, `review_status`, a separate `normalized_hash` for its own duplicate detection, distinct from `question` by construction so a generated item can never be confused with a real PYQ). `GET /api/v1/question/inspired` is honestly empty with a message naming the real reason (no AI provider configured here) — no questions were fabricated to fill it.

**26.6 — Difficulty Intelligence.** `src/domain/difficultyIntelligence.mjs` + `src/repository/difficultyIntelligenceRepository.mjs` + `src/services/difficultyIntelligenceService.mjs`: a *suggested* difficulty delta from real aggregate accuracy/skip-rate (`selected_index IS NULL`, V1)/hint-rate (`hint_used`, V8) — never auto-applied to `question.difficulty`, exactly as the brief says real IRT/Elo calibration is later work. Every response states plainly that this is a single-tenant system — one real learner's history, not a true population — rather than letting "population performance" imply something it isn't.

**26.7 — APIs.** All nine listed endpoints, under the literal `/api/v1/...` paths: `GET /api/v1/pyq`, `GET /api/v1/pyq/:id`, `POST /api/v1/pyq/:id/attempt`, `GET /api/v1/pyq/years`, `GET /api/v1/pyq/topics`, `GET /api/v1/pyq/trends`, `POST /api/v1/ai/hint`, `POST /api/v1/ai/solve`, `POST /api/v1/ai/explain`, `GET /api/v1/question/inspired`.

## Verification performed

**Unit tests** (24 new: 7 `tests/pyq-intelligence.test.mjs`, 10 `tests/pyq-assistant.test.mjs`, 7 `tests/difficulty-intelligence.test.mjs`): frequency reports never divide by zero when empty; the disclaimer is present on every frequency response; progressive hints cumulatively reveal real authored content and clamp into stage 1..4; why-explanations use the real trap only for the option actually picked and report no wrongness when she picked correctly; solve is honest when no real similar question exists; difficulty suggestions report `NONE` confidence below the attempt floor, a positive delta for real low accuracy, a negative delta only when accuracy is high *and* struggle signals are low, and the suggested delta/difficulty are always clamped. 239/239 total unit tests pass (215 existing + 24 new).

**DB-backed exit tests** (`npm run test:pyq-intelligence`, 13 checks; `npm run test:pyq-content-engine`, 21 checks; all passing, real `recordAttempt()` throughout): topic/subject frequency totals match the real 137-question count exactly; yearly trends report only the seven real seeded years; a real transcribed topic (`aptitude.hcf`) reports a real positive concept-frequency count, an untranscribed one reports an honest zero; year/topic/mixed/timed filters return real, correctly-scoped content; weak-area is an honest empty list for a fresh learner, never a guess; incorrect mode returns only questions really answered wrong; three real attempts on one real question feed the assistant and difficulty intelligence correctly, with `learner_topic_state` proven unchanged across every assistant call; asking for assistance on a nonexistent question is refused; the inspired-question endpoint returns genuinely zero fabricated questions.

**Full regression**: `npm test` (239/239) → `npm run db:migrate` (applied `V13__pyq_intelligence`) → `test:pyq-intelligence` (13/13) → `test:pyq-content-engine` (21/21) → all 22 prior DB-backed smoke suites (unaffected, all passing) → `npm run validate:content` (unaffected) → `npm run build` (clean; 10 new routes, including Next.js's static/dynamic sibling routing for `pyq/years`, `pyq/topics`, `pyq/trends` alongside `pyq/[id]`, confirmed working).

**Live verification through the browser**: `GET /api/v1/pyq/trends` returned the real 137-question breakdown across 14 real topics and 7 real years, every disclaimer intact. `GET /api/v1/pyq?topicId=aptitude.hcf&limit=1` returned a real 2016 question. `POST /api/v1/ai/hint` (stage 4), `/ai/solve` (with a real similar question, `hcf-008`) and `/ai/explain` all returned real, grounded content for that question. `POST /api/v1/pyq/hcf-011/attempt` with a real wrong answer updated the real learner's `learner_topic_state` exactly like any other practice attempt (mastery 0.038, `CONCEPTUAL` mistake, real intervention message). `GET /api/v1/pyq/hcf-011` showed the new provenance columns honestly `null`. `GET /api/v1/question/inspired` returned zero questions with the honest reason. All test data on the real learner (`00000000-0000-0000-0000-000000000001`) was deleted afterward, restoring it to its original, pristine, untouched state.

## Known limitations

- **No real PDF/OCR pipeline exists or was built.** 26.1's parser/OCR/detection stages are satisfied by this project's real, working, tested alternative (hand transcription + `validate-content.mjs` + `scripts/seed.mjs`), not by automating the stages the brief literally names. The new `paper`/`question_number`/`source_page` columns are real and ready, but `NULL` on every existing row — genuinely unknown, not fabricated.
- **26.1's full 2011-2025 coverage is not real.** Only 7 of those 15 years have any transcribed content (137 questions), and only two subjects (Aptitude, Reasoning) — the same, repeatedly-documented content-transcription gap named since Phase 1's audit.
- **26.4/26.5 have no live generative AI call in this environment.** The deterministic assistant is the real, honest behavior here — not a stand-in for a "better" version that was skipped. A real provider wrapper already exists elsewhere in the codebase (`src/lib/ai/provider.mjs`) and could, in a future pass, be attempted first with the same graceful-degradation shape before falling back to this phase's deterministic views — not done here because it cannot be verified end-to-end without a real API key in this sandbox.
- **26.6's "population performance" is one real learner's history.** This is a single-tenant system; every difficulty-intelligence response says so explicitly rather than implying a real population exists.
- **26.7's `/api/v1/...` namespace is new and parallel to the existing `/api/...` routes** (including the pre-existing, narrower `/api/ai/hint`) — nothing here modifies or is called by any existing route.

## Algorithm/version changes
