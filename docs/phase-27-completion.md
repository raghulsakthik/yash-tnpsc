# Phase 27 Completion Report — Adaptive Testing, Diagnostics & Recommendation Engine

## The reuse this phase turned on

`assessment`/`assessment_question`/`assessment_answer` (V6/V7, Phase 2/3) were built explicitly as "the forward-looking shape for the assessment types Phase 9+ will add" — only `DEFAULT_TEST` has ever used it. This phase widens one CHECK constraint to add `ADAPTIVE_TEST` and reuses the entire schema (including `metadata JSONB`, where the real blueprint and selection breakdown live) rather than a parallel table — `createAssessment`/`findAssessmentById`/`insertAssessmentQuestions`/`findAssessmentQuestions`/`upsertAssessmentAnswer`/`findAssessmentAnswers`/`findPrerequisiteGraphForTopics`/`findTopicsInSyllabusOrder`/`findRetentionForTopics` are all already generic over `assessment_id` and `type`, confirmed by reading every one of them before writing a line of new code. Phase 10's full diagnostic suite (`summarizeByTopic`, `diagnosePrerequisiteGaps`, `classifyTopics`, `buildTopicRecommendations`, `analyzeSpeedIssues`, `analyzeConfidenceIssues`, `analyzeRetentionIssues`, `deriveStrengthsAndWeaknesses`) is reused unchanged for 27.4. Phase 11's `decideNextActionForTopic()` does the real topic-level scoring for most of 27.5's candidate set. Phase 14's `intervention` table and `startIntervention()`/`listInterventions()` are reused unchanged for 27.6.

## What was implemented

**27.1 Blueprint** (`src/domain/adaptiveTestBlueprint.mjs`): the brief's own category percentages and difficulty distributions as the configured starting point — a category with genuinely nothing real to serve (no revision due; no PYQ content for her current topics; no published `generated_question` rows, which is permanently true in this environment per Phase 26) has its share honestly redistributed, proportionally, rather than reserved for content that doesn't exist.

**27.2 Question Selection** (`src/domain/questionSelectionScore.mjs`): the brief's eight-factor score. `difficultyFit`/`novelty`/`examRelevance` are `selection.mjs`'s own, unchanged, reused directly; `pyqRelevance` reuses `examRelevance()` too (the same real signal, two names); the remaining four factors are computed by the service layer from existing, unchanged sources (`misconceptionRisk`/`prerequisiteRisk` from Phase 6, effective retention from Phase 24, `isRevisionDue` from Phase 11) and only weighed here.

**27.3 Lifecycle** (`src/services/adaptiveTestService.mjs`): `createAdaptiveTest` → `startAdaptiveTest` → `saveAdaptiveTestAnswer` → `submitAdaptiveTest` → `getAdaptiveTestAnalysis`, mirroring `defaultAssessmentService.mjs`'s own structure closely (same grading loop, through the identical `recordAttempt()` call, mode `'ASSESSMENT'`) but driven by the new multi-category blueprint instead of a foundation-only one.

**27.4 Diagnostics** (`src/domain/testDiagnostics.mjs`): two real, new pieces composed onto Phase 10's output. `analyzeMistakePatterns()`/`buildCognitiveProblems()` aggregate the real `mistakeType` every attempt already carries (`mistakes.mjs`'s `classifyMistake()`, unchanged) into guessing/careless/time-pressure counts alongside Phase 10's own overconfidence/underconfidence. `buildRetentionProblems()` composes Phase 15's `compareTopicAcrossTests()` (unchanged) against the learner's most recent other completed assessment (any type) to catch "previously strong, now dropped" — only for topics with real prior evidence, never a guessed baseline.

**27.5 Recommendation Engine** (`src/domain/recommendationEngine.mjs`, `src/services/recommendationService.mjs`): a new `NextBestActionType` enum (named to avoid colliding with the existing, unrelated Phase 4 `RecommendationAction` — caught by a real `SyntaxError` on first test run, see below). `decideNextActionForTopic()`'s own decision for the learner's weakest (or initial gated) topic is mapped onto this broader vocabulary and joined by new candidates this phase adds: `WEAK_AREA_PYQ`/`PYQ` (real PYQ content for that topic, Phase 26), `GAME` (a real active game covering it, Phase 25's `findActiveGameDefinitionForTopic`), and an always-available `WEEKLY_TEST` fallback. Every candidate is scored on the brief's eight factors; `historicalInterventionEffectiveness` reuses real evaluated-intervention history per action type.

**27.6 Intervention Tracking**: the `recommendation` table (V14) makes a scored Next Best Action a real, trackable row (`PENDING`/`ACCEPTED`/`DISMISSED`). Accepting one that targets a topic starts a real, unchanged Phase 14 intervention — verified directly: the real `intervention.topic_id` matches the real `recommendation.target`. `summarizeInterventionEffectiveness()` (new, additive export on `intervention.mjs`) aggregates real `IMPROVED`/`NO_CHANGE`/`REGRESSED` counts from `assessInterventionEffectiveness()` (Phase 14, unchanged) applied to every evaluated row, overall and by action type.

**27.7 APIs**: all twelve routes — the eleven the brief lists under `/api/v1/...`, plus one practical addition (`GET /api/v1/tests/:id`, needed to render a test's questions between creation and submission; not in the brief's literal list but there is no way to answer a test without it).

## A real course-correction, caught on the first test run

The first draft of `enums.mjs` defined a new `RecommendationAction` enum — which already existed, unrelated, since Phase 4 (`diagnostic.mjs`'s narrow `ADVANCE`/`REINFORCE_TOPIC`/`REINFORCE_PREREQUISITE`/`GATHER_EVIDENCE` vocabulary, still actively used and still exactly what it was). `npm test` failed immediately with a real `SyntaxError: Identifier 'RecommendationAction' has already been declared`, cascading to 11 unrelated test files that merely import `enums.mjs` transitively. Renamed the new enum to `NextBestActionType` and re-ran — 269/269. A second, smaller correction followed in the smoke test itself: the first draft tried to prove "a real guess was detected" by making the *first* (correctly-answered) question fast, but `classifyMistake()` only ever classifies a *wrong* answer — fixed by making the first *wrong* answer the fast one.

## Known limitations

- **`completionProbability` and `learnerPreference` are honest placeholders, not measured signals.** No real completion-rate history or preference-tracking exists anywhere in this system yet; both are stated, explicit, neutral defaults (documented inline), not invented data presented as real.
- **`examImportance` in the topic-level candidate is a flat 0.5**, not yet wired to the real `subjectExamWeight()` Phase 23 already computes — a reasonable next increment, not done here to keep this phase's scope to what was asked.
- **The question-selection engine queries per-distinct-topic context sequentially** (cached per topic, not re-fetched per question) rather than in one batched query — acceptable for a once-per-test-creation action, not a hot path, consistent with this project's standing precedent of accepting redundant querying over touching working code.
- **`AI_EXPLANATION`/`MOCK_TEST`/`INSPIRED_MCQ` are real entries in `NextBestActionType` but have no dedicated candidate-builder yet** — `MINI_ASSESSMENT`→`MOCK_TEST` is the only path that currently produces one (via the reused Phase 11 mapping); the others are real, valid values the schema and scoring already support, not yet surfaced by `getRecommendations()`'s candidate set.
